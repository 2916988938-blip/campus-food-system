## 1. 文档概述

### 1.1 项目背景

大学生在校期间经常面临"今天吃什么"的问题：食堂吃腻了、校外餐厅不了解、不知道哪家好吃、不清楚人均消费。现有美食类 App（如大众点评）功能臃肿、信息过载，且缺少针对学生预算和口味的个性化推荐。

本项目旨在做一个**轻量、聚焦**的美食推荐平台，帮助学生快速找到符合自己口味和预算的餐厅。

### 1.2 项目目标

1. 提供一个可按**菜系、价格、评分**筛选的餐厅浏览功能。
2. 支持用户查看餐厅**详情与真实评价**，降低"踩雷"概率。
3. 根据用户填写的**口味偏好与预算**，给出个性化推荐结果。
4. 提供管理员后台，用于维护餐厅数据、管理用户。

### 1.3 适用范围

本项目为课程设计（预备役训练）项目，用于演示前后端分离开发流程，不作为商业系统上线。

### 1.4 读者对象

课程指导老师、项目答辩评审、项目开发者本人。

## 2. 总体描述

### 2.1 产品定位

一款面向在校大学生的**轻量级美食推荐 Web 应用**。核心价值：**快速决定吃什么**。

### 2.2 用户角色

| 角色 | 说明 | 主要权限 |
| --- | --- | --- |
| 普通用户 | 注册登录后的学生用户 | 浏览餐厅、查看评价、收藏、发表评价、接收个性化推荐、维护个人偏好 |
| 管理员 | 系统维护者 | 管理餐厅（增删改查）、管理用户（查看/封禁）、管理菜品 |

### 2.3 业务流程

**主流程（普通用户）：**

```
注册 → 登录 → 浏览/筛选餐厅 → 查看餐厅详情与评价
                              ↓
                    收藏 或 发表评价
                              ↓
                填写口味偏好 → 获取个性化推荐
```

**管理流程（管理员）：**

```
登录 → 进入后台 → 管理餐厅（新增/编辑/上下架）→ 管理用户（查看/封禁）
```

### 2.4 产品环境

- 运行形态：B/S 架构 Web 应用，浏览器访问。
- 前端：Vue 3 + Element Plus。
- 后端：Spring Boot + MySQL，前后端通过 HTTP 接口通信。

## 3. 功能性需求

### 3.1 用户模块

| 编号 | 功能 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| F-USER-01 | 注册 | 用户名、密码、邮箱、昵称 | 注册结果 | 用户名唯一、4-20 位；密码 6-50 位；**邮箱必填且唯一** |
| F-USER-02 | 登录 | 用户名、密码 | Token 凭证 | 密码需加密存储；登录成功签发 JWT；被封禁用户拒绝登录 |
| F-USER-03 | 查看个人信息 | Token | 用户资料 | 需登录 |
| F-USER-04 | 修改个人信息 | 昵称、头像、邮箱 | 更新结果 | 需登录；邮箱修改后仍需唯一 |
| F-USER-05 | 维护口味偏好 | 口味标签、忌口、预算区间 | 更新结果 | 每个用户仅一条偏好记录 |

### 3.2 餐厅模块

| 编号 | 功能 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| F-REST-01 | 餐厅列表 | 页码、每页条数、菜系、价格区间、关键词 | 分页列表 | 默认按评分排序；仅显示营业中餐厅（status=1） |
| F-REST-02 | 餐厅详情 | 餐厅 ID | 餐厅详情 + 菜品列表 | 不存在时返回 404 |
| F-REST-03 | 关键词搜索 | 关键词 | 匹配的餐厅列表 | 匹配名称、菜系、标签 |
| F-REST-04 | 餐厅管理（管理员） | 餐厅信息 | 操作结果 | 新增/修改/删除/上下架 |

### 3.3 评价模块

| 编号 | 功能 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| F-REV-01 | 发表评价 | 餐厅 ID、评分(1-5)、内容 | 评价结果 | **同一用户对同一餐厅仅保留一条评价**；已存在评价时引导走"修改评价"（F-REV-03），不新增第二条 |
| F-REV-02 | 查看评价列表 | 餐厅 ID、分页参数 | 评价列表 | 按时间倒序 |
| F-REV-03 | 修改/删除评价 | 评价 ID | 操作结果 | 仅能操作自己的评价 |

> 评价新增/修改/删除后，**餐厅平均分需自动重算**（见业务规则 4）。
>
> 本项目**不做评价点赞功能**。

### 3.4 收藏模块

| 编号 | 功能 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| F-FAV-01 | 收藏餐厅 | 餐厅 ID | 收藏结果 | 同一餐厅不可重复收藏 |
| F-FAV-02 | 取消收藏 | 餐厅 ID | 取消结果 | — |
| F-FAV-03 | 我的收藏列表 | 分页参数 | 收藏列表 | 仅自己可见 |

### 3.5 推荐模块

| 编号 | 功能 | 输入 | 输出 | 约束 |
| --- | --- | --- | --- | --- |
| F-REC-01 | 个性化推荐 | 用户偏好（口味、预算） | 推荐餐厅列表（含推荐理由与得分） | 用户未填偏好时给出默认推荐（高分餐厅） |
| F-REC-02 | AI 智能推荐（第 6 周） | 用户自然语言描述 | 推荐结果 | 调用大模型 API，密钥保存在服务端 |

> **推荐结果为实时计算，不落库**：每次请求按下方算法现场计算并返回，不留推荐记录。
> 本版本**不提供"喜欢/不喜欢"反馈功能**，因此不设反馈数据表。

**推荐算法（初级阶段）说明：**

采用**加权打分**规则，对每家候选餐厅计算得分后排序：

```
score = 口味匹配度 × 0.4
      + (评分 / 5) × 0.3
      + 价格适配度 × 0.2
      + 热度（评价数） × 0.1
```

- **口味匹配度**：餐厅标签与用户偏好标签的重合比例 = 重合标签数 ÷ 用户偏好标签总数（0~1）。
- **价格适配度**：餐厅人均价格落在用户预算区间内记满分 1；低于区间下限记 1（更便宜也接受）；高于区间上限时按 `1 - (超出金额 ÷ 区间上限)` 线性衰减，最低 0。
- **热度**：评价数归一化，本项目简化为 `min(评价数 ÷ 20, 1)`。
- **候选集**：营业中（status=1）的餐厅，按得分取 Top 10。
- 本算法为**简化实现**，用于演示推荐流程，不追求工业级精度。

## 4. 非功能性需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 单次接口响应时间 < 1 秒（本地环境）；列表查询支持分页，单页不超过 20 条 |
| 兼容性 | 支持 Chrome / Edge 最新版浏览器；页面适配 1366px 及以上分辨率 |
| 安全性 | 密码使用 bcrypt 加密存储；接口使用 JWT 鉴权；管理接口需管理员角色；AI 密钥等敏感信息存于服务端，不暴露给前端 |
| 易用性 | 核心操作（找餐厅、评价）不超过 3 次点击；表单有校验与错误提示 |
| 可维护性 | 后端采用 Controller / Service / Mapper 分层；接口统一返回格式 `{ code, message, data }`；统一异常处理 |

## 5. 数据需求

- 数据库：MySQL 8.0，字符集 utf8mb4。
- 共 **6 张表**：`user`、`preference`、`restaurant`、`dish`、`review`、`favorite`。
- 表结构、字段说明、索引、外键约束详见 `docs/数据库设计文档.md` 与 `sql/schema.sql`。
- ER 关系：

```
user 1:1 preference
user 1:N review      N:1 restaurant
user 1:N favorite    N:1 restaurant
restaurant 1:N dish
```

## 7. 业务规则

1. 用户名、邮箱全局唯一；注册与修改个人信息时均需校验。
2. 同一用户对同一餐厅**仅保留一条评价**，可通过"修改评价"更新（F-REV-03），不新增第二条；评分范围 1-5。
3. 同一用户对同一餐厅**只能收藏一次**。
4. 餐厅平均分 = 该餐厅所有评价评分的平均值，保留 1 位小数；评价变更后自动重算。**无评价的餐厅评分记为 0，标记为"暂无评分"，排序时排在有评分餐厅之后。**
5. 推荐结果实时计算，不落库。
6. 被封禁（status=0）的用户无法登录；**封禁仅禁止登录，其历史评价与收藏数据保留**，不再新增内容。
7. 营业中（status=1）的餐厅才出现在用户端列表；休息中（status=0）的餐厅不出现在用户端。
